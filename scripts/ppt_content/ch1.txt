#SECTION 讲次 1-2 · Streaming 流式输出
#PAGE 为什么必须流式
• 推理延迟秒级起步,长输出数十秒
• 串行等待:用户盯着白屏离开
• 流式:首字延迟 <1s,体验质变
• 附加收益:用户可提前取消省 Token
#PAGE SSE 协议本质
• HTTP 长连接 + 文本事件流
• 帧格式:data: {json}\n\n
• 结束标记:data: [DONE]
• 单向服务端推送,浏览器原生支持
>>比 WebSocket 轻,够用就是最好
#TERM SSE 打字机实测输出|$ curl -N -X POST :8000/v1/chat/completions;data: {"delta": "worl", "usage": null};data: {"delta": "d, f", "usage": null};data: {"delta": "rom ", "usage": null};data: {"delta": "", "usage": {"total_tokens": 626}};data: [DONE];# 末帧强制携带 usage → 成本留痕数据源|平台真实输出

#PAGE FastAPI 流式转发
• StreamingResponse 包装 async 生成器
• media_type=text/event-stream
• 逐块转发,不做全量缓冲

• 浏览器:EventSource 或 fetch 流读取

#PAGE 中断与取消
• 用户点击停止 → 关闭连接
• 服务端检测写失败即终止推理
• 省下的是真金白银的 Token
>>取消也必须留痕:用量已产生部分
#STATE 流式会话状态|streaming,paused,done,cancelled;streaming->paused:网络抖动;paused->streaming:自动重连;streaming->done:[DONE];streaming->cancelled:用户停止;paused->cancelled:超时|已生成部分保留+计量

#PAGE 流式异常处理
• 网络抖动:连接中断而非报错
• 限流:可能在流中途触发
• 策略:已收内容保留 + 提示重试
• 禁止整段重流造成双倍计费
#PAGE 长文本断点保存
• 会话断开 → 丢弃还是续传?
• 方案:持久化已生成内容+序列号
• 恢复:从断点继续生成
• 本平台:任务摘要即恢复锚点
>>断点续传是长文任务的刚需
#PAGE 踩坑:缓冲毁掉流式
• 反向代理默认缓冲响应体
• 现象:打字机变成"憋大招"
• 修复:nginx 加 X-Accel-Buffering: no
• 自检:curl 必须逐块可见
#PAGE 踩坑:SSE 帧粘包
• 两帧数据连在同一个 chunk 里
• 解析器按 \n\n 切分才能还原
• 修复:跨 chunk 维护行缓冲
>>协议细节在集成测试里暴露

• 上游不带时按内容长度合成
