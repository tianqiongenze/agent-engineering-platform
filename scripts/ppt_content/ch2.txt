#SECTION 讲次 2-1 · Function Calling 与 Tool Use 原理
#PAGE 本章问题域
• 模型会说,但不会做
• 目标:让模型安全地"用手干活"
• 三层:机制(FC)/治理(Runtime)/协议(MCP)
• 对应工程:src/agent_platform/tools/
#ARCH Tool Runtime 全景|注册:Tool Registry,元数据,版本,启停;执行:权限,Schema 校验,超时,重试;审计:InMemory,Pulsar 适配(降级),哈希链;外部:MCP Client,文件/DB/GitHub|flow=注册,治理,审计

#PAGE Function Calling 是什么
• 模型不执行任何代码
• 只输出"我想调 toolX,参数是{...}"
• 执行权永远在 Runtime 手里
>>意图与执行分离是安全的第一性
#PAGE 一次工具调用的完整时序
• ① 请求携带工具定义清单
• ② 模型返回 tool_calls 意图
• ③ Runtime 校验并执行
• ④ 结果以 role=tool 回灌
• ⑤ 模型基于结果继续推理
#PAGE 工具定义的七要素
• name:唯一且动词化
• description:给模型看的说明书
• parameters:JSON Schema
• 返回/错误结构约定
• 权限等级 + 风险等级
>>描述写不好,模型就选错工具
#GRID 工具契约七要素|name:动词化唯一名;description:给模型看的说明书;parameters:JSON Schema;返回结构:Output Schema;错误结构:Error Schema;权限等级:READ/WRITE/DANGEROUS|cols=3

#PAGE 三份契约:Input/Output/Error
• Input Schema:参数合法性
• Output Schema:结果可消费
• Error Schema:失败可处理
>>契约三方共享:模型/Runtime/审计
#PAGE 工具选择机制
• 模型按任务语义匹配工具
• 依据:name + description + 参数说明
• 多工具相似 → 选择抖动
• 缓解:描述差异化 + few-shot 示范
#PAGE 模型不选工具怎么办
• 描述太抽象,模型没信心
• 参数必填太多,模型绕开
• 优化:拆细工具 + 简化必填
>>工具设计是 Prompt 设计的一部分
#PAGE 工具治理全景图
• 校验 → 权限 → 执行 → 审计
• 超时/重试/降级/恢复
• Trace 全链路留痕
>>第2章代码就是这张图

#SECTION 讲次 2-3 · 工具治理与安全边界
#PAGE 治理四道防线
• 参数校验:挡脏数据
• 权限分级:挡越权
• 人工确认:挡高危
• 审计回放:事后可追
>>平台 ToolExecutor 即四道串联
#PAGE 参数校验:Schema 即法律
• Pydantic 严格校验类型/必填/范围
• 拒绝多余字段(防注入)
• 错误信息结构化返回
>>校验失败不进执行,直接审计留痕
#PAGE 权限模型:RBAC 三角色
• readonly:仅 READ 工具
• agent:READ + WRITE
• admin:全部(含 DANGEROUS)
>>身份透传:用户权限决定工具权限
#TABLE RBAC 风险矩阵,角色,READ 工具,WRITE 工具,DANGEROUS 工具;readonly,✓,✗,✗;agent,✓,✓,需确认凭据;admin,✓,✓,需确认凭据|hl=3|实测:readonly 调高危 → PermissionDeniedError

#PAGE 高危工具:确认凭据制
• DANGEROUS 一律拒 readonly
• 执行必须带 confirmed=True
• 平台 drop_database 演示拦截
>>无确认执行=安全事故
#STATE 工具调用状态|PENDING,PERMIT_OK,EXECUTING,AUDITED,REJECTED,TIMEOUT;PENDING->PERMIT_OK:权限通过;PERMIT_OK->EXECUTING:wait_for 执行;EXECUTING->AUDITED:结果落审计;EXECUTING->TIMEOUT:超时降级;PENDING->REJECTED:readonly/未确认|

#SECTION 讲次 2-4 · MCP 协议与接入
#PAGE MCP 是什么
• Model Context Protocol
• 连接模型与外部工具/资源的标准协议
• Client/Server 架构
• Anthropic 开源,已成行业趋势
#SEQ MCP 调用时序|Agent,MCP Client,MCP Server,外部资源 |0->1:发现工具清单;1->2:tools/call(参数);2->3:执行(受白名单约束);3->2:结果+元数据;2->1:结构化返回;1->0:观察回灌|三层权限:Server/工具/参数

#PAGE FC 与 MCP 的分工
• Function Calling:模型怎么选工具
• MCP:工具怎么标准化接入
• 一个管意图,一个管生态
>>两者互补而非竞争
#PAGE MCP 三大能力
• Tools:可执行的函数
• Resources:可读的数据源
• Prompts:预置提示模板
>>一个 Server 同时暴露三类
#PAGE MCP vs 传统 HTTP API
• 自描述:发现而非硬编码
• 标准化:一次接入处处可用
• 会话化:连接复用与状态
>>更适合 Agent 的动态场景
#ARCH MCP 生态接入层|Agent 运行时:Loop+Decider;MCP Client:发现,调用,连接池;MCP Server 群:文件系统,数据库,GitHub,内部 API;治理:白名单,审计,脱敏|flow=发现,调用,治理

#PAGE 架构位置:防腐层
• MCP Client 藏在 Runtime 后面
• 上层不感知 Server 差异
• Server 挂了 → 工具自动摘除
>>DDD 防腐层的教科书案例
